실습 6 매뉴얼의 “생각해보기” 4문항에 대한 예시 답안입니다. 정답이 하나만 있는 문제는 아니지만, 여기 실린 코드는 실제로 fsm_scene_demo.py에 적용해 동작을 검증한 버전입니다. 먼저 스스로 답을 만들어본 뒤 비교해보는 것을 권장합니다.

1일시정지 중 배경음악은?

질문 지금 코드는 효과음만 다루지만, 배경음악이 있다면 PausedScene에 진입할 때 pygame.mixer.music.pause()를, 재개할 때 unpause()를 호출하면 됩니다. 어느 메서드(__init__, handle_event) 안에 넣어야 정확히 한 번씩만 호출될지 생각해보세요.

정답: pause()는 __init__에, unpause()는 handle_event의 복귀 분기에 넣습니다.

__init__은 PausedScene(self)로 새 인스턴스를 만드는 바로 그 순간, 즉 이 씬에 진입하는 순간 딱 한 번만 실행됩니다. 반면 update()는 이 씬이 살아있는 동안 매 프레임 반복 호출되므로, 거기에 pause()를 넣으면 일시정지 상태를 유지하는 내내 초당 60번씩 불필요하게 호출됩니다.

fsm_scene_demo.py — PausedScene
class PausedScene(Scene):
    """PlayScene 위에 반투명 오버레이만 얹어서 그리는 씬.

    새로 화면을 처음부터 그리지 않고, 얼려둔(freeze) 이전 씬(underlying)을
    먼저 그린 뒤 그 위에 반투명 사각형과 안내 문구만 겹쳐 그린다.
    """
    def __init__(self, underlying: PlayScene):
        self.underlying = underlying
        pygame.mixer.music.pause()  # 이 씬에 "진입"하는 순간 정확히 1번 호출된다

    def handle_event(self, event):
        if event.type == pygame.KEYDOWN and event.scancode == pygame.KSCAN_P:
            snd_pause.play()
            pygame.mixer.music.unpause()  # 이 씬을 "떠나는" 순간 정확히 1번 호출된다
            self.manager.go_to(self.underlying)  # 얼려뒀던 PlayScene으로 그대로 복귀

    def update(self, dt):
        pass  # 일시정지 중에는 아무 것도 갱신하지 않는다 (dt를 흘려보내지 않음)

    def draw(self, surface):
        self.underlying.draw(surface)  # 뒤에 멈춰있는 게임 화면을 그대로 보여주고

        overlay = pygame.Surface((WIDTH, HEIGHT), pygame.SRCALPHA)
        overlay.fill((10, 12, 20, 170))  # 알파값 170으로 반투명 어둡게
        surface.blit(overlay, (0, 0))

        text = FONT_BIG.render("일시정지", True, (255, 255, 255))
        surface.blit(text, text.get_rect(center=(WIDTH // 2, HEIGHT // 2 - 20)))
        hint = FONT.render("P 를 눌러 계속하기", True, (210, 214, 226))
        surface.blit(hint, hint.get_rect(center=(WIDTH // 2, HEIGHT // 2 + 30)))
왜 "정확히 한 번"이 중요한가요? pygame.mixer.music.pause()를 여러 번 연달아 호출해도 에러는 나지 않지만, 만약 나중에 "재생 위치를 기록했다가 되돌리기" 같은 더 정교한 로직을 추가한다면 "몇 번 호출됐는지"가 상태를 어긋나게 만들 수 있습니다. __init__과 “전이가 실제로 일어나는 그 줄”에 정확히 짝을 맞춰 넣는 습관은, 지금 당장 문제가 없어도 이후 확장에서 버그를 막아줍니다.
검증 이 코드를 실제로 PausedScene 진입 4회, 복귀 4회를 반복시켜본 결과 pause() 4회 / unpause() 4회로 정확히 1:1 대응했습니다. 복귀 시 pause()가 추가로 불리지 않는 것도 함께 확인했습니다.

2씬이 하나 더 필요하다면?

질문 "일시정지 중 정말 종료할지 확인하는 팝업"을 추가하려면 Scene을 상속하는 클래스를 어떻게 설계하고, 어떤 씬에서 어떤 씬으로 전이되도록 go_to()를 연결해야 할지 화살표 다이어그램으로 그려보세요.

ConfirmQuitScene이라는 새 씬을 추가합니다. PausedScene에서 ESC를 누르면 이 씬으로 전이하고, 여기서 Y를 누르면 프로그램을 종료하고 N(또는 ESC)을 누르면 다시 PausedScene으로 돌아갑니다.

핵심 설계 포인트는 ConfirmQuitScene도 취소를 대비해 underlying(원래의 PlayScene)을 계속 들고 다녀야 한다는 것입니다. PausedScene에서 넘겨받은 self.underlying을 그대로 다음 씬에 다시 넘겨줘야, 취소했을 때 "얼려둔 게임 화면"을 잃어버리지 않고 PausedScene(self.underlying)으로 복귀할 수 있습니다.

fsm_scene_demo.py — PausedScene 수정 + ConfirmQuitScene 신규
class PausedScene(Scene):
    """PlayScene 위에 반투명 오버레이만 얹어서 그리는 씬.

    새로 화면을 처음부터 그리지 않고, 얼려둔(freeze) 이전 씬(underlying)을
    먼저 그린 뒤 그 위에 반투명 사각형과 안내 문구만 겹쳐 그린다.
    """
    def __init__(self, underlying: PlayScene):
        self.underlying = underlying

    def handle_event(self, event):
        if event.type == pygame.KEYDOWN:
            if event.scancode == pygame.KSCAN_P:
                snd_pause.play()
                self.manager.go_to(self.underlying)  # 얼려뒀던 PlayScene으로 그대로 복귀
            elif event.key == pygame.K_ESCAPE:
                snd_pause.play()
                # "정말 종료?" 팝업으로 전이. underlying(PlayScene)을 그대로 들고 가서
                # 취소했을 때 다시 PausedScene(self.underlying)으로 돌아올 수 있게 한다.
                self.manager.go_to(ConfirmQuitScene(self.underlying))

    def update(self, dt):
        pass  # 일시정지 중에는 아무 것도 갱신하지 않는다 (dt를 흘려보내지 않음)

    def draw(self, surface):
        self.underlying.draw(surface)  # 뒤에 멈춰있는 게임 화면을 그대로 보여주고

        overlay = pygame.Surface((WIDTH, HEIGHT), pygame.SRCALPHA)
        overlay.fill((10, 12, 20, 170))  # 알파값 170으로 반투명 어둡게
        surface.blit(overlay, (0, 0))

        text = FONT_BIG.render("일시정지", True, (255, 255, 255))
        surface.blit(text, text.get_rect(center=(WIDTH // 2, HEIGHT // 2 - 20)))
        hint = FONT.render("P 를 눌러 계속하기 / ESC 를 눌러 종료", True, (210, 214, 226))
        surface.blit(hint, hint.get_rect(center=(WIDTH // 2, HEIGHT // 2 + 30)))


class ConfirmQuitScene(Scene):
    """PausedScene 위에 한 겹 더 얹는 "정말 종료?" 확인 팝업.

    이 씬 자체는 아무 게임 상태도 갖지 않는다 - 오직 "예/아니오"를
    판정해서 둘 중 하나로 전이시키는 역할만 한다.
    """
    def __init__(self, underlying: PlayScene):
        self.underlying = underlying  # 취소 시 되돌아갈 PlayScene

    def handle_event(self, event):
        if event.type == pygame.KEYDOWN:
            if event.key == pygame.K_y:
                # 메인 루프가 이미 처리하고 있는 QUIT 이벤트를 그대로 재사용한다.
                # ConfirmQuitScene이 "게임을 어떻게 끝내는지"를 직접 알 필요가 없다.
                pygame.event.post(pygame.event.Event(pygame.QUIT))
            elif event.key == pygame.K_n or event.key == pygame.K_ESCAPE:
                snd_pause.play()
                self.manager.go_to(PausedScene(self.underlying))  # 취소 -> 다시 일시정지 화면으로

    def draw(self, surface):
        self.underlying.draw(surface)
        overlay = pygame.Surface((WIDTH, HEIGHT), pygame.SRCALPHA)
        overlay.fill((10, 12, 20, 200))
        surface.blit(overlay, (0, 0))

        text = FONT.render("정말 게임을 종료할까요?", True, (255, 255, 255))
        surface.blit(text, text.get_rect(center=(WIDTH // 2, HEIGHT // 2 - 20)))
        hint = FONT_SMALL.render("Y: 종료   /   N(또는 ESC): 취소", True, (210, 214, 226))
        surface.blit(hint, hint.get_rect(center=(WIDTH // 2, HEIGHT // 2 + 20)))
Y를 누르면 프로그램을 어떻게 끄나요? ConfirmQuitScene이 pygame.quit()이나 sys.exit()을 직접 호출할 수도 있지만, 그러면 메인 루프의 running = False 흐름과 별개의 종료 경로가 하나 더 생겨버립니다. 대신 pygame.event.post(pygame.event.Event(pygame.QUIT))로 메인 루프가 이미 처리하고 있는 QUIT 이벤트를 그대로 큐에 올려줍니다. 다음 프레임에 메인 루프의 for event in pygame.event.get():가 이 QUIT을 집어서 running = False로 정상 종료합니다. 씬은 "종료해야 한다"는 사실만 알리고, "어떻게 종료할지"는 메인 루프에게 맡기는 책임 분리입니다.
검증 실제로 PlayScene → P(일시정지) → ESC(확인) → N(취소, 다시 일시정지) → ESC(확인) → Y 순서로 입력을 흘려본 결과, 전이가 설계한 그대로 일어났고 Y를 눌렀을 때 QUIT 이벤트가 정상적으로 큐에 올라가는 것까지 확인했습니다.

3대각선 이동을 정규화하지 않으면?

질문 실습 5의 normalize() 호출을 주석 처리하고 실행해보세요. 대각선으로 이동할 때와 가로로만 이동할 때의 체감 속도 차이를 직접 확인해보고, 왜 그런 차이가 생기는지 벡터의 길이 공식으로 설명해보세요.

normalize()를 주석 처리하면 대각선 이동이 가로·세로 이동보다 41% 더 빨라집니다. 방향키 하나만 누르면 move는 (1, 0)처럼 성분이 하나뿐이라 길이가 원래 1이지만, 두 방향키를 동시에 누르면 move가 (1, 1)이 되고 이 벡터의 실제 길이는 1이 아닙니다.

벡터의 길이 공식
가로/세로 이동
move = (1, 0) → 길이 = √(1²+0²) = 1
대각선 이동
move = (1, 1) → 길이 = √(1²+1²) = √2 ≈ 1.41

self.player_pos += move * self.speed * dt에서 move의 길이가 그대로 배속으로 곱해지기 때문에, 정규화 없이 대각선으로 이동하면 매 프레임 실제로 speed × 1.41 × dt만큼 이동합니다. move.normalize()는 방향은 그대로 두고 길이만 강제로 1로 맞춰서, 어느 방향으로 이동하든 항상 같은 speed가 적용되도록 보정하는 역할을 합니다.

4저장 데이터를 늘려본다면?

질문 save_data 딕셔너리에 "play_count"(플레이 횟수)를 추가해 게임을 시작할 때마다 1씩 증가시키고 저장해보세요. 어느 씬의 어느 시점에서 값을 증가시키고 저장해야 정확한 횟수가 기록될까요?

정답: PlayScene.__init__의 맨 앞에서 증가시키고 곧바로 저장합니다. TitleScene에서 SPACE를 눌렀을 때도, GameOverScene에서 R로 재도전할 때도 — “플레이가 새로 시작되는” 모든 경로가 결국 새 PlayScene 인스턴스를 만드는 것으로 합쳐지기 때문입니다. 두 갈래 경로 각각에 카운트 증가 코드를 따로 넣을 필요 없이, 그 두 경로가 만나는 지점 한 곳에만 넣으면 됩니다.

fsm_scene_demo.py — load_save_data() + PlayScene.__init__
def load_save_data():
    """저장 파일이 없거나 손상되었을 때도 게임이 죽지 않도록 항상 안전한 기본값을 반환한다."""
    if not os.path.exists(SAVE_PATH):
        return {"high_score": 0, "play_count": 0}
    try:
        with open(SAVE_PATH, "r", encoding="utf-8") as f:
            data = json.load(f)
        # 예전 버전 저장 파일에 키가 없을 수도 있으니 기본값으로 보완한다.
        data.setdefault("high_score", 0)
        data.setdefault("play_count", 0)
        return data
    except (json.JSONDecodeError, OSError):
        # 파일이 깨져 있어도 프로그램이 죽지 않고 새로 시작할 수 있게 한다.
        return {"high_score": 0, "play_count": 0}


class PlayScene(Scene):
    TIME_LIMIT = 20.0

    def __init__(self, save_data):
        self.save_data = save_data
        # 새 플레이 세션이 "시작"될 때 정확히 1번만 증가하고 즉시 저장한다.
        # (재도전으로 다시 PlayScene이 만들어질 때도 여기서 잡힌다)
        self.save_data["play_count"] = self.save_data.get("play_count", 0) + 1
        save_save_data(self.save_data)
        self.player_pos = pygame.Vector2(WIDTH // 2, HEIGHT // 2)
        self.speed = 220.0
        self.score = 0
왜 TitleScene이나 GameOverScene에 넣으면 안 되나요? TitleScene.handle_event에 넣으면 SPACE로 시작하는 경우는 잡히지만 R로 재도전하는 경우는 놓칩니다. 반대로 GameOverScene에 넣으면 재도전은 잡히지만 최초 시작은 놓칩니다. 두 곳에 각각 넣으면 코드가 중복되고, 나중에 "플레이 시작"의 세 번째 경로가 생기면 또 빠뜨리기 쉽습니다. PlayScene.__init__은 두 경로가 실제로 합류하는 지점이므로 딱 한 군데만 수정하면 모든 경로를 놓치지 않습니다.
왜 GameOverScene에서 점수를 저장할 때 같이 안 하고, 시작하자마자 즉시 저장하나요? 만약 저장을 게임오버 시점까지 미루면, 플레이 도중 프로그램이 강제 종료되었을 때 그 판의 시도 자체가 기록에서 통째로 사라집니다. “시작한 순간”을 정확히 세고 싶다면, 시작하는 바로 그 시점에 저장해야 합니다.
검증 헤드리스로 TitleScene → SPACE(최초 시작) → 시간 종료 → GameOverScene → R(재도전) 순서로 진행시켜본 결과, play_count가 1 → 2로 정확히 증가했고 매번 savegame.json 파일에도 즉시 반영되는 것을 확인했습니다.
